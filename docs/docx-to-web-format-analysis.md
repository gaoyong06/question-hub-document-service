# Docx 解析换行与格式还原：问题分析与最佳实践

## 一、当前现象

- **表现**：试卷在网页预览时出现「该换行的地方没换行、不该换行的地方有换行」，阅读混乱。
- **目标**：将 docx 的版式**尽量原封不动**转为网页展示。

## 二、当前实现简要梳理

### 2.1 解析链路（docx）

1. **段落提取**（`document_parser.py`）
   - 使用 `python-docx`：按 `doc.paragraphs` 遍历，每个段落内按 `run` 拼接文本并处理图片。
   - 每个 **Word 段落** 得到**一行**：`line = "".join(parts).strip()`，非空则加入 `paragraphs`。
   - 全文：`full_text = "\n".join(paragraphs)`，即**仅用「Word 段落」作为换行**。

2. **题目切分**
   - 用正则从 `full_text` 中匹配题干、选项、答案等（如单选题的 `_extract_single_choice_with_pos`）。
   - 题干/选项等 content 来自 `m.group(1).strip()` 等，**中间可能包含 `\n`**（来自原段落边界）。

3. **前端展示**
   - 试卷详情页用 `MarkdownDisplay` 渲染 `question.content`，即**已按 Markdown 渲染**。

### 2.2 导致换行错乱的主要原因

| 层级 | 原因 |
|------|------|
| **解析** | Word 的**段内软换行**（`<w:br/>`）未被保留。当前是「一段 = 一行」，段内换行全部丢失 → **该换行的地方没换行**。 |
| **解析** | 若卷子中题干/选项用多个 Word 段落排版，`full_text` 里会有大量 `\n`；正则用 `.+?` 在 `re.DOTALL` 下跨行匹配，题干/选项边界容易错位 → **不该换行的地方被当成多段或错位**。 |
| **展示** | 标准 Markdown 中**单个 `\n` 不产生换行**（需双换行或「两空格+换行」）。若 content 是「纯文本 + 单 `\n`」，前端不会显示为换行 → **该换行的地方没换行**。 |

## 三、是否有必要「整体用 Markdown」？

- **结论：有必要，且与「原封不动转网页」目标一致。**
- 理由简要说明：
  1. 前端已经用 **Markdown**（`MarkdownDisplay`）渲染题目内容，只给图片用 Markdown 而正文不用，会继续出现「有 `\n` 但前端不换行」的问题。
  2. Markdown 能表达：段落、换行（双 `\n` 或行尾两空格 + `\n`）、列表、加粗等，足够覆盖试卷常见版式，且便于后续扩展（公式、图片已支持）。
  3. 在**解析阶段**就输出「带结构的 Markdown」（段落/换行正确），比在前端用正则或启发式「修」纯文本更可控、可维护。

因此：**整体内容（题干、选项、答案、解析）在解析/存储层面就按 Markdown 输出，而不仅给图片用 Markdown**，是合理方向。

## 四、行业常见做法（Docx → 网页保真）

1. **Docx → HTML**
   - 保留段落、标题、加粗、列表等，输出语义化 HTML（`<p>`, `<br/>`, `<strong>` 等），前端用安全 HTML 渲染。
   - 优点：最保真、与 Word 结构一一对应。缺点：需解析 OOXML 样式与结构，实现成本高。

2. **Docx → Markdown**
   - 用 **Pandoc**、**MarkItDown** 等将 docx 转为 Markdown（保留标题、列表、换行等），再在业务里从 Markdown 解析题目或直接展示。
   - 优点：Markdown 易存、易渲染、易扩展（公式、图片）；与你们当前前端的 `MarkdownDisplay` 一致。缺点：需要约定「题目边界」如何在 Markdown 中识别（或先转 Markdown 再按规则切题）。

3. **保留文档结构 + 题目切分**
   - 从 Word 按「段落 + 段内换行」提取，生成**带换行/段落的中间表示**（如 Markdown 或简单 HTML），再在这之上做题目识别与切分（题干、选项、答案），保证题干/选项内部换行正确。
   - 这是当前项目更适合的路线：在现有 python-docx 解析上增强「段内换行」与「输出 Markdown」，再配合前端已有 Markdown 渲染。

## 五、推荐方案（在现有架构下）

### 5.1 原则

- **解析**：保留 Word 的**段落边界**与**段内软换行**（`<w:br/>`），使「该换行处」在中间表示里就有换行。
- **中间表示**：题干/选项/答案等**统一用 Markdown**（含换行、段落、图片），便于前端原样渲染。
- **展示**：继续使用现有 `MarkdownDisplay`，保证单换行在 Markdown 中有效（见下）。

### 5.2 解析层：保留段内换行

- 在 `_extract_paragraphs_with_images` 中，不仅按 `para.runs` 拼接，还要**按段落 XML 顺序**处理：
  - 遍历 `para._element` 子节点；
  - 对 `w:r`：取 run 文本（及已有图片占位逻辑）；
  - 对 `w:br`：在对应位置插入一个换行（例如输出 `\n` 或 Markdown 的 `  \n`）。
- 这样「一段内」的软换行会反映到当前段的字符串里，再进入 `full_text` 和后续题目 content，就不会出现「该换行没换行」。

### 5.3 输出为 Markdown 换行规范

- Markdown 中「单行换行」需**行尾两空格 + 换行**或**双换行**（新段落）。建议：
  - 在写入题目 `content`（及 options、answer、explanation）时，将**单 `\n`** 统一转为 **`  \n`**（行尾两空格 + 换行），这样前端 `react-markdown` 会正确显示为换行；
  - 或：段落之间用 `\n\n`，段内换行用 `  \n`，这样既保真又符合 GFM。

### 5.4 题目切分与「不该换行处」

- 当前用正则从 `full_text` 切题，若 Word 里一道题的题干/选项被拆成很多段落，`full_text` 里会多出大量 `\n`，容易导致：
  - 题干被截断或包含下一题内容；
  - 选项与题干粘连或错位。
- 建议：
  - **短期**：在现有正则上微调，或先按「段落列表」做题目边界检测（如题号、答案：、解析：），再在「段落块」内用 `\n` 或 `  \n` 连接，避免跨题匹配。
  - **中长期**：考虑「先按结构生成整卷 Markdown，再按题号/答案/解析等锚点切分题目」，使题目 content 的换行完全由 Word 结构决定，减少正则带来的错位。

### 5.5 可选：非 docx 格式（如 PDF）的 Markdown 管道

- 你们已有 MarkItDown（PDF 等 → Markdown），若 PDF 解析后也得到 Markdown，可复用「题目 content 统一为 Markdown」的约定，前端展示逻辑一致。

## 六、三个环节：目的与原则

**目的**：将用户上传的文档（Word、PDF、PowerPoint、Excel、图片、文本、EPUB 等）中的**格式完整、忠实地转换为 Markdown**，并正确显示出来，与源文档格式一致。

**原则**：
- **不在各环节里写「自定义格式逻辑」**。用户文档格式五花八门，针对某一类格式的合并/拆分规则，在另一种格式下可能错误。正确性应通过**三个环节各司其职、忠实转换**来保证。
- **环节 1**：解析源文档，输出**忠实反映源文档结构**的中间表示（如段落、段内换行、同一行/不同行）。同一行就应输出为同一段或同一行，不应在环节 2 用规则去「猜」合并。
- **环节 2**：把环节 1 的中间表示**原样映射**到 Markdown（有换行就写 `\n`，同一行就不写换行）。不在环节 2 做「按题型合并/拆分」等自定义处理。
- **环节 3**：用 Markdown 正确渲染，不改变结构。

---

### 六.1、题干与选项换行问题定位

| 环节 | 职责 | 题干与选项换行问题中的表现 |
|------|------|----------------------------|
| 1. 解析 docx | 按段落/段内换行提取，得到 `paragraphs` 与 `full_text = "\n".join(paragraphs)` | 正确：题干与 "A." 在不同段时，full_text 中已有 `题干\nA.\n...` |
| 2. 反映在 markdown | 从 full_text 切出题干/选项并写入 content、options | **问题**：正则中 `(.+?)\s+(A\. ...)` 的 `\s+` 消耗了题干后的换行，但 content 只存了 group(1).strip()，**没有把 docx 的段落边界写入 content** |
| 3. Markdown 显示 | 前端用 Markdown 渲染 content | 若 content 中带 `\n\n`，会正确分段；之前因环节 2 未写入断行而显示成一行 |

**修复原则**：在**环节 2** 把 docx 的段落边界忠实写入 markdown（如 content = 题干 + `\n\n`），不在环节 2 写「合并选项与图」等自定义逻辑；若源文档里选项与图同一行，应由**环节 1** 输出为同一段/同一行，环节 2 只做忠实映射。

### 六.2、「选项字母与图同一行」问题：三个环节定位

| 环节 | 职责 | 在本问题中的表现 |
|------|------|------------------|
| 1. 解析 docx | 按 Word 段落输出，得到 `paragraphs` | 若 docx 里「A.」与图**实际在同一行**（同一段或同一行布局），环节 1 应输出**一段**（如 `"A. {{IMAGE_0}}"`），而不是两段。若当前输出两段，需在**环节 1** 改进解析（如识别「同一行」的段落/布局），使输出与源文档一致。 |
| 2. 反映到 markdown | 把环节 1 的输出**原样映射**到 content、options | 只做忠实映射：环节 1 给出一段就写一段、给出两段就写两段并保留 `\n`。**不应**在环节 2 写「把仅图片段与上一段合并」等自定义逻辑。 |
| 3. Markdown 显示 | 前端用 Markdown 渲染 | 按存库内容渲染即可。 |

**结论**：若 docx 里选项与图同一行，正确做法是**环节 1** 解析出「同一行」结构（一段或带同一行语义的表示），**环节 2 只做忠实映射**。不在环节 2 写合并/拆分等自定义规则。

### 六.3、「看图写数」多图与答案括号同一行：三个环节定位

| 环节 | 职责 | 在本问题中的表现 |
|------|------|------------------|
| 1. 解析 docx | 按 Word 段落/布局输出，得到 `paragraphs` | 若 docx 里多图与「( )」**实际在同一行**，环节 1 应输出**一段**（如 `"{{IMAGE_0}} {{IMAGE_1}} ... ( )"`），而不是多段。若当前输出多段（每图一段），需在**环节 1** 改进解析（如按 Word 的「同一行」/布局输出为一段），使输出与源文档一致。**不应**在环节 2 用「合并仅图段」等自定义逻辑补救。 |
| 2. 反映到 markdown | 把环节 1 的输出**原样映射**到 content | 只做忠实映射：环节 1 给出一段就写一段、多段就用 `\n` 连接。不在环节 2 写「连续仅图段用空格连接」等规则。 |
| 3. Markdown 显示 | 前端渲染 content | 按存库内容渲染即可。 |

**结论**：若 docx 里多图与括号同一行，正确做法是**环节 1** 解析出「同一行」结构（一段），**环节 2 只做忠实映射**。不在环节 2 写合并规则。

## 七、小结

| 问题 | 建议 |
|------|------|
| 该换行没换行 | 解析时保留段内 `<w:br/>`，输出时把单 `\n` 转为 Markdown 换行（`  \n` 或 `\n\n`），整体用 Markdown 存储/展示。 |
| 题干与选项之间换行 | 问题在「反映在 markdown」环节：提取时 content 未包含题干后的段落边界。应在提取单选题/多选题时把「题干后的段落断行」写入 content（如 content = 题干 + `\n\n`），而不是在后续统一处理里按题型补逻辑。 |
| 不该换行有换行/错位（选项与图、多图与括号同一行） | 正确做法：**环节 1** 解析时按源文档「同一行」输出为一段（或带同一行语义），**环节 2 只做忠实映射**。不在环节 2 写「合并仅图段」「合并选项与图」等自定义逻辑，以免在其它格式下出错。 |
| 是否整体用 Markdown | **有必要**；题干/选项/答案/解析都使用 Markdown，与前端 `MarkdownDisplay` 一致，便于原样还原版式。 |
| 行业实践 | Docx→HTML 最保真但成本高；Docx→Markdown + 题目切分 更贴合现有技术栈，也便于扩展公式与图片。 |

实现上可优先做两件事：  
1）**环节 1**：在 `_extract_paragraphs_with_images` 中按 `para._element` 处理 `w:br`，输出带段内换行的段落文本；并保证「源文档同一行」在解析结果中为同一段（或同一行语义），不依赖环节 2 的合并规则。  
2）**环节 2**：把环节 1 的输出**原样映射**到 markdown（题干后段落边界 → content 末尾 `\n\n` 等），不写「合并仅图段」「合并选项与图」等自定义逻辑。前端（环节 3）只负责正确渲染。
